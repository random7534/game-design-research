## 这些结果怎样改变 Skill

- **先确认交付对象。** 局部原型可以回答规则问题；原作内改造还要保留用户要评估的交互、表现和流程。不能把两种任务替换掉。已修改入口、原型参考和 C07。
- **把后果实际走到下一次选择。** 对 A→B 与 B→A 分别执行，确认新资格、已完成成果和结局。休整是放弃部分机会的选择，不意味着被跳过的日期客观上无事可做。已修改状态/叙事、成长、C09 与 C20。
- **模型的前提不算测试结果。** 指明哪些来自已读数据或调用路径，哪些人为设为成功；核对单位、每份/整单、舍入和资源所属容器。重复同一个谓词不增加独立覆盖。已修改案例方法和 C22。
- **先核实测量条件，再归因。** 保留实际交付格式及声道、增益等转换；控制表演与时序后再比较音效，技术完整性与真人判断分别报告。已修改原型、试玩、生产及 C18。
- **让说明对应实际裁定。** 预览、手动/自动、计数与恢复只在已执行范围内验收，不能由源码中存在某分支就写成运行通过。已补入案例方法与 C21。

六条既有候选 C07、C09、C18、C20、C21、C22 得到条件和验证方式的修订，没有增加同义候选。方法仍为 proposed；本轮执行证明局部规则或制作检查可用，尚无跨项目玩家效果验证。

## 对错误记录怎样处理

声音反馈最初把单声道混合后的峰值当作双声道交付峰值，并归为编码过冲。独立解码在相同文件上复现了声道转换差异，原会话随后修订脚本和报告，三个交付音频保持原文件。这是验证口径的纠正，不能继续以旧解释充当成功修复案例。

生产模型的首次复核发现当前输入与旧指纹不齐；之后匹配快照的隔离复跑与最新结果一致。保留前后记录，不根据当前通过结果猜测最初差异的原因。派遣测试中人工构造事件即使标为 live，也不证明模型请求发生；真实生成、缓存、回退与规则执行另有来源记录。

原始证据不公开时，读者只能审阅本库的匿名总结与适用范围，不能将它当作可独立重放的公开实验。方法与案例的双向定位见 [候选表](candidates.md)、[案例记录](../skills/game-design-development/references/case-observations.json)；验证层次见 [验证记录](validation.md)。

## 卡图修订的后续回收

同一卡牌项目随后按重复人物构图的反馈，把三张图改为功能不同的物件或动作特写，结合轮廓、方向、明暗与底色区分。素材和部署记录已有文件级检查，最终手牌显示及新版战斗尚未验收；早期规则版的操作记录不能替新版通过。通用检查已加入动作反馈参考和 C28，不公开角色素材或未公开设定。

2026-10-25 的后续只读核对又区分了冻结试玩包与开发候选：新身体已有原生动作录帧记录，冻结包仍使用旧备用身体，正式退出、恢复和长局检查尚未完成。已将“修订另存、证据对应实际包内资产”的要求补入生产参考。没有运行或改写用户正在使用的包，也不把动作片段当作完整游戏验收。

## 游戏内文案

本轮同时补入技能、卡牌、按钮和提示的简洁要求。前端只显示玩家当下判断与操作需要的规则；实现说明、测试状态、来源位置及“某处已标注”等交付备注放项目文档。复杂规则按需展开，简短表达仍要准确。该约束进入 Skill 和玩法简表，实际项目的界面清理按各自当前版本继续执行。

外部研究和通用方法保存于公共库；项目未公开内容保留本地。没有修改个人认可台账。
