# 游戏设计与开发

完成当前委托的可评审成果。研究用于帮助做决定，用户要求实现时继续到可运行结果；用户只要求研究、评审或局部修改时遵守范围。这里的方法来自外部研究与本次综合，不代表用户已认可其为个人立场。

## 开始工作

已有项目先读本次任务相关的约定、设计、代码和最近测试证据；纯方案任务只读实际需要的材料。判断当前问题属于体验、规则、表达、技术还是制作能力；不要把已有可玩项目重新当作空白立项。

从上下文确认目标玩家、平台与输入方式、期望体验、当前阶段、可用资源和交付目标。只追问会改变下一步选择的缺口；其余用明确的可撤销假设继续。引擎、商业化、联网、长期运营、AI运行时都按实际需要选，不作为默认配置。

如果存在 `$CODEX_HOME/game-design-development.local.json`（未设置时用 `~/.codex/`），按其中路径读取本地知识库规则与认可台账。该配置只提供定位信息，不授予发布、外部写入或扩大任务的权限。缺少配置时仍可独立完成游戏工作。

## 从体验推到实现

1. 用具体行为描述期望体验。例如“玩家看到追兵后仍愿意冒险绕路救人”，并说明什么观察会推翻这一预期。紧张、探索、表达、沉思、熟练和社交可以有不同的验证方式。
2. 写出最小交互链：玩家感知到什么 → 可以做什么 → 规则如何裁定 → 世界发生什么变化 → 玩家如何理解后果。重复发生的链才称循环；线性短作无需硬加成长、刷取或付费循环。
3. 明确规则接口：前置条件、行动成本、状态变化、结算顺序、随机信息和终止/恢复方式。表达性选择也可能有价值，用相应体验验证，不只按数值变化判断。
4. 找到最危险的假设，选择能观察到它的最低成本形式。动作手感要用交互原型；策略可先桌面推演；叙事可先试读或角色扮演，但不能拿试读证明移动端操作已成立。
5. 完成验证后，记录保留、修改或删除的决定和依据。用户委托实现时推进到所需交付，不把一次纸面验证当作完成整款游戏。

需要记录时按用途选用 [game-brief.md](assets/templates/game-brief.md)、[playtest-log.md](assets/templates/playtest-log.md)、[decision-record.md](assets/templates/decision-record.md)、[release-evidence.md](assets/templates/release-evidence.md)。小改动不强制新建文档。

## 实现与验收约束

- 游戏玩法循环与程序逐帧循环分开讨论。让规则状态可以核对，画面、音效和对白表达已经发生的结果；架构复杂度与当前问题相称。
- 实现完整的委托范围，包括进入、关键行动、反馈、结束或暂停退出、再次进入/恢复等适用路径。沙盒、叙事短作不强制胜负、资源稀缺或传统关卡。
- 验证实际风险：非法状态、关键分支不可达、重复结算、存读档污染、输入与可读性、目标设备性能。只为重要行为写有意义的测试；自动测试无法替代真实玩家的体验反馈。
- 报告时分别写清静态检查、自动运行、人工试玩、目标设备测试、导出、平台审核和正式发布的证据。缺少哪个就说明哪个；可下载的数据包不自动等于可运行游戏。
- 新研究仍是外部研究；实验成功仍是实验结果。只有用户明确认可具体主张及其范围，才能写入个人认可库，并保留原始来源、认可记录和后续修订。

## 交付表达

先说当前完成的结果，再给决定依据、验证和剩余限制。列出实际改动、文档、构建位置与版本；不要为一次功能修复附整套通用策划书，也不要把编译成功表述为游戏已被证明好玩。
