# 外部研究、项目实验与个人认可

出处和认可状态是两条独立信息。官方文档可能准确描述工具行为，但不因此成为用户的个人价值判断；用户认可某种设计观点，也不消除它原有的出处与适用限制。

## 保存规则

| 层 | 保存内容 | 进入条件 |
|---|---|---|
| 外部来源 | 作者、标题、URL、日期、访问日、原意、限制 | 已实际读取，注明全文、部分或摘要覆盖 |
| 候选综合 | 来源到操作建议的推导、反例、验证方法 | 明确标为本次综合，仍待认可 |
| 项目实验 | 条件、构建、过程、结果、失败与解释 | 有真实执行证据，不自动推广到全部项目 |
| 个人认可 | 用户认可的准确主张、范围、理由与原话依据 | 用户明确认可该主张，保留来源链 |

“收集一下”“整理好”“放进外部知识库”、关注或收藏、某次实验成功，均不直接等同对主张的认可。用户明确说“我认可某条做法用于某类项目”时可以登记该范围，无需再次要求形式确认。指代不明时保留待确认，不猜测其认可全部研究。

认可记录包含条目 ID、准确表述、适用与不适用条件、原始来源、用户依据与日期、项目证据、修订状态。用户只认可一部分时提取该部分，不能连带接受整篇文章、作者或全部候选观点。撤回或修订保留历史和原因，更新当前可用观点及相关索引。

默认个人台账不公开。公网库只发布本次授权的外部材料链接、简短原创摘要与通用综合，先检查是否混入个人经历、私有仓库、未公开作品、账号信息、本地路径、访问令牌或第三方大段原文。公开摘要不会让原作改换许可；不整篇搬运。

## 从项目或会话回收方法

先定位实际报告、规则、实验或原作者资料，记录版本和本轮读取范围。会话摘要用于寻找证据，转发建议及其复述不算独立确认；尚未执行的改版保留提案身份。先保留原始反馈与对应输入，再核查脚本、实际退出和产物；发现测量或归因错误时修订当前主张并记录新证据。没有旧版产物或失败日志时，当前回归通过不等于独立复现了历史失败。详见 [案例迁移工作法](case-derived-planning.md) 与 [案例证据表](case-observations.json)。

提炼内容应改变后续策划的具体判断，保留来源能支持的范围、适用条件、反例与验证办法。复用已有原则时补充例子或条件，避免新增同义规则。公共库可以保存原创概括和可公开的来源入口；私有路径、会话原文、未公开创意与原作代码/资源留在本地审计；可由本地配置的 `project_applications_root` 定位。项目应用提案也不等于个人认可。项目有局部证据，不代表提炼的方法已被玩家验证或被用户认可。

## 检索与来源判断

先按当前设计问题选来源，再交叉核对不同观点。论文检验其具体实验目标；开发者复盘保留项目条件和幸存者偏差；官方文档核对版本与接口；社区笔记用于发现实践问题。热度与权威身份都不能代替对主张的具体核验。

小红书只记录实际看到的公开内容与稳定链接。只见标题、搜索摘要、视频封面或片段时说明覆盖，不用标题还原全文；不把平台相对日期臆测为完整日期，不把访问参数公开。用户授权浏览不自动授权收藏、评论、关注或投稿。

后续维护由新任务触发，不据此自行创建定时检索、公开发布、修改旧个人文章或同步私有库的自动任务。更新外部方法后检查与现有认可条目的关系，不能静默替换用户已接受的表述。
