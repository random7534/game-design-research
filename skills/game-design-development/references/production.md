# 从原型到交付

这些阶段用于解决不同问题，可以重叠或简化。极小型作品可能不需要单独的纵向切片里程碑；已有项目从当前风险进入，不反复重建立项文档。

| 阶段 | 要回答的问题 | 足够进入下一阶段的证据 | 常见误判 |
|---|---|---|---|
| 体验与范围假设 | 谁为什么想玩，团队准备做多大 | 有可解释目标、边界和最危险假设 | 题材有热度就认定玩法成立 |
| 可玩原型 | 关键行动或判断是否产生预期体验 | 对应任务的行为观察与可重复试玩 | 界面能点、系统齐全就认定好玩 |
| 纵向切片 | 一小段内容能否达到目标品质并走通生产流程 | 有代表性的代码、资产、音频、内容、测试和目标平台构建 | 只做视觉样片，没有生产与集成证据 |
| 生产 | 剩余内容能否按已知成本完成 | 可复用管线、依赖顺序、实际产量、范围调整 | 依据理想开发速度线性外推 |
| 发布候选 | 当前版本能否稳定交付给目标玩家 | 构建身份、关键路径与设备证据、资产及平台要求核验 | 编译、导出、审核通过、已发布混为一谈 |
| 发布后 | 哪些问题值得修复或扩展 | 实际问题与目标玩家反馈 | 指标一跌就补日常、广告或付费系统 |

Godot 的纵向切片案例强调以代表性成品验证技术与制作；其细节仍须按团队和作品调整。[PROD-01] 原型阶段允许低成本替代资产；需要验证美术可读性或目标设备性能时，替代资产必须接近该风险。Rami Ismail 的文章进一步强调原型围绕设计疑问选择保真度，并在需要时联合多个机制。[Q01] 玩法任务的具体保留边界见 [原型与失败成本](prototype-and-challenge.md)。

## 原游戏内改造

REA、逆向任务先区分分析与实施。任务或本地工作约定要求原作内修改时，通过原游戏的 Mod、配置、资源、脚本或补丁接入，在原运行环境中验证；按需求修改原有交互与流程。未经用户明确要求，不把独立新游戏、换引擎重制或网页演示替代为这项交付。只有分析委托时，保持分析范围。

规则、音频和界面小原型可辅助验证具体问题，但须说明哪些结果尚未接入原游戏。接入受阻就继续查入口、版本依赖和可复核缺口，不自行把任务改成独立重写。保护原安装和原存档，运行修改优先使用隔离副本及独立存档。

交付写清对应原游戏版本、修改范围、实际启动入口及运行结果。独立原型能运行、静态分析完整或规则模型通过，均不能据此声称原作内修改已经生效。

## 把范围换算为工作

列出必须有、可删除、暂缓的内容，以及各自服务的体验。按依赖安排工作：规则成立之后再扩张依赖该规则的大量内容。为最不确定的资产、工具链或设备限制做小验证，避免所有风险都留到尾部。

用已经做过的代表性单元估算制作与返工成本，另记集成、音频、适配、测试、商店材料和发布处理。没有历史数据时明确标为估计，用下一个代表性单元校准。阶段是否继续由证据和约束决定，不用普遍适用的“原型必须几天”取代判断。

资产记录来源、许可、修改范围和依赖。临时素材、未授权参考、占位字体与生成资产的使用条件在发布前逐项确认；不把联网服务或采集玩家数据当成必需品。

## 架构和性能随风险推进

规则数据、内容数据、存档与表现之间保持能说明的边界。复用项目已有组织，不为了模板强制重写。版本控制与可恢复备份服务于可追溯交付，不能通过丢弃他人改动来恢复整洁。

设计时考虑性能预算，在实际目标设备上用分析工具定位瓶颈，再修改和复测。既不要逐行凭感觉优化，也不要等完成所有内容才第一次测设备。[PROD-04] 帧率、内存、加载、发热或网络延迟的目标取决于平台和体验，本文不设通用合格数值。

可访问性从文字与对比、输入、声音、运动效果和认知负担选取相关项；按玩法保留可玩性并允许调整。微软 XAG 是设计指导，不能当成法律或平台认证，也不能用清单代替相关玩家测试。[PROD-06][PROD-07]

## 仓库维护与远端同步

用户要求制作期间同步 GitHub 时，按已完成且可复查的工作单元提交并推送。先核对当前项目的仓库根目录、远端和上游，沿用已有对应仓库与可见性；确无对应远端时，按用户授权建立私有仓库，避免重复建库。多会话共用工程时协调文件归属和提交责任人，普通冲突保留双方改动，不通过丢弃工作或改写历史恢复整洁。

提交应包含可复现所需的源码、内容生成源、自制必要资产、依赖和构建运行说明。凭据、账号配置、本地存档、原游戏完整安装及商业游戏原始资源留在项目约定的本地范围；可重建的大文件记录生成方法与指纹，不能因忽略必要自制资产导致远端无法构建。

推送后核对远端分支与提交 SHA，再报告仓库链接及同步范围；本地提交、推送成功和远端可构建分别判断。推送失败保留本地成果并说明具体卡点，不能声称已经上传。本地配置中的 `repository_maintenance` 只记录用户的既有选择，执行仍须符合当前任务与项目的授权范围。

## 版本与发布

记录提交、构建编号、平台、引擎与依赖版本、导出配置、产物位置和必要哈希。用同一发布候选版本对应验收与发布材料。检查实际交付文件及其解码/转换条件；无损中间文件的精确相等不自动扩展到有损格式，转换时的增益也不能误归因为内容或编码缺陷。变更后重跑受影响的关键验证，不依赖旧版本截图宣称新版本通过。

用户正在试玩的冻结包保持不变，修订另存版本，并说明每份包实际包含的规则与资产。探针录帧、正式运行、退出和恢复分别记录；新素材通过探针不能提升旧包状态，资源生命周期改动还需核对正式程序的退出与真实读档。

恢复测试使用真实保存点和实际恢复入口，核对加载后的关键状态；只检查存档字段不等于已经续玩。业务断言、进程退出码、运行期错误与退出期资源告警分别报告，退出 0 不代表整个日志零告警。

Godot 的 PCK/ZIP 数据导出不一定包含可执行运行环境；导出预设与含凭据的文件须分开管理。[PROD-05] Steam Playtest、商店审核、构建审核和正式发行也是不同操作。[PROD-08][PROD-09] 设备兼容性按实际目标验证，不把自测称为 Valve 官方认证。[PROD-10] 用户要求发布时按其授权推进；普通设计或本地制作委托不自动授予公开上传、付款或消息发送权限。
